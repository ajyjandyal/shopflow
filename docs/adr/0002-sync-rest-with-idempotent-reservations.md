# ADR 0002: Synchronous REST between services, with idempotent stock reservations

**Status:** Accepted (Phase 2). Expected to be partly superseded in Phase 4 (Kafka).

## Context
Splitting the monolith gives each service its own database. Checkout used to be one
local ACID transaction (lock products, decrement stock, insert order, clear cart). Stock
now lives in product-service's database and orders in order-service's, so no single
transaction can cover both. We also need to survive the realities of a network: calls
can time out, and a timed-out call may or may not have been executed.

## Decision
1. order-service calls product-service over HTTP (Spring `RestClient`) with explicit
   connect/read timeouts.
2. Stock is taken through a **reservation** whose id (UUID) is generated by the caller.
   `reserve` and `release` are **idempotent**: repeating them has no additional effect.
   Concurrency per reservation id is serialised with `INSERT ... ON CONFLICT DO NOTHING`
   followed by `SELECT ... FOR UPDATE`.
3. A `release` for an unknown id stores a RELEASED **tombstone**, so a delayed `reserve`
   that arrives afterwards is rejected.
4. order-service retries `reserve` (max 3 attempts, linear backoff) only on ambiguous
   failures (timeout, connection refused, 5xx). Definite failures (409) are never retried.
5. If the order can't be saved after a successful reservation, order-service
   **compensates** by releasing the reservation (a simple, orchestrated Saga).
6. Cancel releases stock *before* updating the order, so a failed local update can be
   retried safely.
7. Internal endpoints (`/internal/**`) are not routed by the gateway and require a shared
   `X-Internal-Api-Key` header.

## Consequences
- Positive: no overselling; safe retries; no distributed transactions (2PC) needed;
  services own their data.
- Negative: checkout availability now depends on product-service being up (temporal
  coupling). If the compensating `release` also fails, stock stays reserved with no
  order; this is logged as `COMPENSATION FAILED` and must be fixed manually.
- Phase 4 replaces steps 4–5 with events (Kafka) and a transactional outbox, removing
  the "compensation failed" gap and the temporal coupling.

## Alternatives considered
- **Two-phase commit (XA):** strong consistency, but blocking, slow, poorly supported by
  modern infrastructure, and couples services' availability tightly.
- **Shared database:** simplest, but services would no longer be independently
  deployable and schema changes would break each other.
